# Alert catalog

## Status and required owner input

This catalog defines the minimum alert contracts for P7-006. It does **not** claim that a production monitoring provider, notification route, threshold, or on-call rotation has been configured. P7-005 telemetry is a dependency and remains the source of final metric names.

Before production use, the service owner must fill every `TBD` below, configure the alerts in the chosen monitoring system, and capture a test notification. An alert is not operational until its owner and escalation route are reachable.

## Notification payload requirements

Every configured notification must include:

- stable alert name and severity;
- environment and start time;
- dashboard/query link and the matching runbook;
- primary owner and escalation route;
- sanitized symptoms and correlation identifiers, never cookies, OAuth codes, tokens, credentials, SQL contents, student names, or protected record payloads;
- current alert state (`firing` or `resolved`); and
- acknowledgement and resolution timestamps when supported.

## Alert validation checklist

- [ ] Final owner, backup owner, and incident commander are recorded for each alert.
- [ ] Thresholds and evaluation windows are based on observed staging baselines.
- [ ] Each alert has been triggered safely in staging and delivered to the configured route.
- [ ] Redaction of notification labels, annotations, and linked logs has been reviewed.
- [ ] Duplicate suppression and missed-notification behavior are understood.
- [ ] Database-outage and OAuth-outage tabletop exercises have been completed and recorded; the plans in `tabletop-exercises/` are not evidence of execution.
