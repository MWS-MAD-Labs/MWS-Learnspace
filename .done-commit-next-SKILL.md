# Done, Commit, Next

Use this workflow to finalize the current task quickly and safely.

## 1. Inspect the current work

- Read the repository status and diff before changing anything.
- Identify the task being completed from the conversation, changed files, branch context, and project documentation.
- Preserve all intended user and agent changes. Do not discard, overwrite, or revert unrelated work.
- Check for untracked secrets, credentials, generated junk, debug artifacts, or unexpectedly large files before committing.
- If the intended task cannot be determined safely, ask the user instead of guessing.

## 2. Validate completion

- Run the most relevant focused tests, type checks, lint, formatting checks, builds, or diagnostics supported by the repository.
- Prefer existing project scripts and commands documented in `package.json`, contributor docs, CI configuration, or task documentation.
- Reuse recent validation results from the current conversation when they are still valid for the current working tree. Rerun checks affected by later edits.
- Fix failures caused by the current work when practical.
- Do not commit if there are unresolved correctness failures, suspected secrets, or merge conflicts. Explain the blocker to the user.
- Do not claim a check passed unless it was actually run and passed.

## 3. Update documentation

- Find the project’s task tracker or roadmap, commonly `docs/ROADMAP.md`.
- Mark the current task complete if it is not already complete.
- Add or update a concise completion note containing:
  - The major behavior delivered.
  - Important security, authorization, persistence, or lifecycle guarantees.
  - The validation that passed.
  - The completion date when the surrounding document uses dates.
- Update other directly relevant documentation, such as generated API specifications or changelogs, only when the repository’s established workflow requires it.
- Do not mark deferred or unimplemented work complete.

## 4. Determine the next task

- Read forward from the completed task in the primary roadmap.
- Select the first incomplete item whose declared dependencies are complete.
- Prefer the immediate next numbered task when it is actionable.
- Record its identifier, title, dependencies, acceptance requirement, and validation expectations for the final response.
- If no roadmap exists, identify the clearest follow-up from explicit TODOs or documentation. Label this as an inference.

## 5. Review and commit

- Recheck `git status` and inspect the final diff summary.
- Confirm generated files are current when the repository tracks them.
- Commit all intended staged and unstaged changes, including relevant untracked files.
- Never include secrets, temporary test output, editor files, or unrelated artifacts.
- Use a concise conventional commit message when the repository has no stronger convention, for example:
  - `feat: migrate FEDC observations`
  - `fix: finalize observation lifecycle`
  - `docs: complete roadmap item`
- Use one commit unless the user explicitly requests multiple commits.
- Do not push, create a branch, tag a release, or open a pull request unless explicitly requested.
- After committing, verify the commit exists and report whether the working tree is clean. If intentional files remain, list them.

## 6. Respond to the user

Provide a concise final report with:

- **Done:** What was completed and which documentation was updated.
- **Commit:** Commit hash and subject.
- **Validation:** Commands or suites that passed.
- **Next:** The next actionable task, including its key acceptance requirement and recommended first step.
- **Working tree:** Clean, or a precise list of remaining files and why they were not committed.

Do not ask whether to commit: invoking this skill is explicit authorization to update documentation and commit all intended current changes.
